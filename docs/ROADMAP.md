# 教会礼拝出席管理 SaaS ロードマップ

- 作成日: 2026-06-14
- 方針: 単一教会での実運用品質を完成させてから、他教会展開と課金へ進む
- 仕様書: `docs/PRODUCT_SPEC.md`

## 全体方針

最短で「多機能なSaaS」を作るのではなく、次の順番を守る。

1. 現行データを失わない。
2. 認証・マルチテナント・RLSを先に完成させる。
3. 日曜受付の操作速度と信頼性を完成させる。
4. 永福南キリスト教会で4週間以上パイロット運用する。
5. 他教会のオンボーディングを整える。
6. 継続利用の意思を確認してから課金する。

## Phase 0: ベースライン確立

目安: 1〜2日

### 目的

安全に大規模変更へ入るため、現状を再現・検証可能にする。

### 実装項目

- 現行画面、API、DBスキーマ、環境変数を整理する。
- `README.md` を実プロジェクト用に更新する。
- `.env.example` を新しい命名方針へ更新する。
- 現行DBのバックアップ・移行手順を文書化する。
- テスト基盤を追加する。
- 現行主要フローのスモークE2Eを追加する。
- 日付・タイムゾーンの扱いを `Asia/Tokyo` 前提で確認する。

### 完了条件

- `npm run lint` と `npm run build` が成功する。
- 現行の「朝礼拝出席」「昼食」「夕拝」「ゲスト追加」「CSV出力」をテストで再現できる。
- 破壊的なDB移行前に戻せる手順がある。

## Phase 1: 安全なマルチテナント基盤

目安: 3〜5日

### 目的

他教会展開の前提となるデータ分離とログインを完成させる。

### 実装項目

- Supabase AuthのSSR構成を導入する。
- ログイン、ログアウト、保護ルートを実装する。
- `churches`、`profiles`、`church_memberships` を追加する。
- `people`、`service_events`、新 `attendance_records` を追加する。
- 立場と年齢区分を分離する。
- 全テナントテーブルへ `church_id` を追加する。
- `anon_all` ポリシーを廃止する。
- owner/admin/receptionist/viewerのRLSを実装する。
- RLS分離テストを追加する。
- 既存Supabaseデータの移行スクリプトを作る。

### 完了条件

- 未認証ユーザーは人物・出席データを読めない。
- 教会Aのユーザーは教会Bのデータを読めず、書けない。
- 通常処理でservice role/secret keyを使っていない。
- 既存の人物・出席・昼食データを新スキーマへ件数一致で移行できる。
- 既存受付フローが新スキーマで動く。

## Phase 2: 日曜運用MVP

目安: 4〜7日

### 目的

永福南キリスト教会で、Excel転記なしに日曜運用できる状態へする。

### 実装項目

- 礼拝イベント選択・作成を実装する。
- 朝礼拝、夕拝、特別礼拝を同一モデルで扱う。
- 受付画面を新データモデルへ最適化する。
- 昼食数量を入力できるようにする。
- ゲスト追加、重複候補、人物統合を実装する。
- 大人・子ども・立場別のリアルタイム合計を表示する。
- 複数端末の更新をRealtimeまたは再取得で同期する。
- 通信失敗時の再試行キューと未同期表示を実装する。
- 直前操作の取り消しを実装する。
- 監査ログを実装する。

### 完了条件

- 受付担当が既存人物を2タップ以内で登録できる。
- ゲストを30秒以内で追加できる。
- 4台の端末で同時操作しても重複・集計ずれが起きない。
- 通信を一時的に切っても、復帰後に入力が同期される。
- 特別礼拝を通常礼拝の出席率から除外できる。

## Phase 3: 集計・移行・Google Sheets

目安: 4〜6日

### 目的

現在のExcel運用を置き換え、必要なデータを外部へ持ち出せるようにする。

### 実装項目

- ダッシュボードと期間集計を実装する。
- 朝・夕・特別礼拝、昼食、大人・子ども、立場別集計を実装する。
- 出席率を `counts_toward_attendance_rate` 対象イベントから算出する。
- CSV出力を新データモデルへ移行する。
- Google OAuth接続を実装する。
- `drive.file` を基本とする最小権限でGoogle Sheets出力を実装する。
- `まとめ`、`出席マトリクス`、`ゲスト`、`人物一覧` を出力する。
- 現行Excelの一度限りの移行スクリプトを作る。
- 移行結果の件数・合計照合レポートを作る。

### 完了条件

- 画面、CSV、Google Sheetsの主要合計が一致する。
- 現行Excelの人物・通常礼拝・特別礼拝を移行できる。
- 元Excelを変更しない。
- Google接続解除後にトークンを利用できない。

## Phase 4: 単一教会パイロット

目安: 最低4週間

### 目的

実際の日曜運用で、速度・信頼性・分かりやすさを検証する。

### 実施項目

- 永福南キリスト教会で主記録として利用する。
- 初回2週は紙またはExcelをバックアップとして併用する。
- 受付担当から操作上の迷いを記録する。
- 集計差異、同期失敗、重複人物を毎週レビューする。
- 重大障害時の復旧手順を確認する。
- 機能追加より、入力速度と信頼性の問題を優先修正する。

### 完了条件

- 4週連続で重大なデータ消失がない。
- 礼拝後の転記作業がほぼ不要になる。
- 受付担当が継続利用を希望する。
- 集計値がバックアップ記録と一致する。

## Phase 5: 他教会向けベータ

目安: 1〜2週間 + ベータ期間

### 目的

開発者の手作業なしで、別教会が安全に利用開始できる状態へする。

### 実装項目

- 教会作成オンボーディングを実装する。
- ownerによるユーザー招待とロール管理を完成させる。
- 初期人物CSVインポートを実装する。
- 教会設定、子ども表示名、タイムゾーン設定を実装する。
- 利用状況とエラーの運用監視を追加する。
- データエクスポート・退会時削除手順を整える。
- サポート用ドキュメントを作る。

### 完了条件

- 2教会以上が開発者のDB操作なしで利用開始できる。
- 教会間データ分離テストが継続的に成功する。
- ベータ教会から継続利用の意思が得られる。

## Phase 6: 課金

目安: 3〜5日

### 開始条件

- パイロット以外の教会が継続利用している。
- 少なくとも複数教会が有料利用の意思を示している。
- サポート工数と運用コストを把握できている。

### 実装項目

- 教会単位でStripe Customerを作成する。
- Stripe Billing + Checkout Sessionsで月額契約を開始する。
- Customer Portalを接続する。
- webhookで契約状態を同期する。
- 契約状態に応じた機能制御を実装する。
- 解約・支払失敗時の猶予期間とデータ出力を実装する。

### 完了条件

- Checkout完了、更新、支払失敗、解約がwebhook経由で正しく反映される。
- 課金画面の戻りURLだけで権限を付与しない。
- 解約した教会が自分のデータを出力できる。

## 優先度

### P0: 本番前に必須

- 認証
- 教会単位RLS
- 現行データ移行
- 礼拝イベントモデル
- 高速な受付
- 通信失敗時の保護
- RLS・集計・主要E2Eテスト

### P1: パイロット中に完成

- Google Sheets出力
- Excel移行
- 人物統合
- 監査ログ
- 複数端末同期
- オンボーディング

### P2: 価値検証後

- 課金
- 高度な分析
- 複数メニューの食事管理
- より柔軟なカスタムイベント

## 実装しない順序

- 認証とRLSより先に課金を作らない。
- イベントモデルより先に複雑な集計を増やさない。
- 単一教会パイロットより先に大規模な他教会向けカスタマイズをしない。
- Google Sheets同期を受付の正規データ保存先にしない。
- 現行データのバックアップなしで破壊的移行をしない。
